# Agent UX design

## Summary

This design adds first-class agent support to Plane's HW fork across backend and frontend. The system has two agent types: external agents (registered third-party services reached via webhooks) and a built-in agent (runs inside the Django/Celery stack). The built-in agent uses a code-generation approach: the LLM produces executable code, which runs in a sandboxed subprocess. That sandbox communicates with the host process via newline-delimited JSON over stdin/stdout, calling a typed tool registry that enforces the triggering user's permissions before touching the ORM. Activity records — thoughts, code blocks, tool results, final responses — are written to the database and streamed to the frontend via SSE (Server-Sent Events) over Redis pub/sub.

The UI work has three parts: a workspace settings panel for managing agent registrations (following the existing webhook management pattern), @mention autocomplete that routes to webhook dispatch or the internal execution task depending on agent type, and a persistent right-sidebar chat panel for multi-turn conversation with the built-in agent. All new UI lives in `apps/web/hw/` with CE stubs in `apps/web/ce/` that satisfy the same TypeScript interfaces with null or empty implementations. The eight implementation phases proceed in dependency order, with the data model first and the UI last.

## Definition of Done

This design covers four interconnected deliverables that together form a complete agent experience for the Plane HW fork:

**1. Agent management UI** — A workspace settings panel where admins can register, edit, and deactivate agents (both external webhook-based agents and the built-in agent), view agent runs across issues, and manage credentials and webhook configuration.

**2. Agent mention autocomplete** — The @mention dropdown in the rich text editor includes registered agent names alongside users. Selecting an agent triggers a run (webhook dispatch for external agents, internal execution for the built-in agent). The built-in agent responds as comments in the issue timeline, using the same mechanism as external agents.

**3. Agent chat UI** — A conversational panel (not scoped to a single issue) where users can interact with the built-in agent in multi-turn dialogue, see reasoning and actions streamed in real-time, and direct the agent to operate across the workspace (create issues, update cycles, query data, etc.).

**4. Built-in agent runtime** — A Phoebe-inspired sandboxed execution layer extending the existing LiteLLM backend. The LLM generates code that executes in a sandbox with access to Plane API tools via a typed interface. Reachable via both the chat UI and @mentions in issue comments.

**Out of scope:** MCP server (blocked by upstream OAuth dependency), building the agent as an externally hosted service, exact replication of Phoebe's architecture, comprehensive tool coverage beyond an MVP tool set.

## Acceptance criteria

### agent-ux.AC1: Agent management UI

- **agent-ux.AC1.1 Success:** Workspace settings shows an "Agents" page listing all registered agents (both external and built-in) with display name, type badge, and active status.
- **agent-ux.AC1.2 Success:** Admin can register a new external agent via modal — form accepts display name, description, webhook URL, and webhook secret. On creation, API token is displayed once.
- **agent-ux.AC1.3 Success:** Agent detail page shows editable configuration fields and a recent runs table with status, trigger type, linked issue, and timestamps.
- **agent-ux.AC1.4 Success:** Built-in agent card is always present (auto-seeded), shows configuration options (model override, tool permissions, active toggle), and cannot be deleted.
- **agent-ux.AC1.5 Success:** Admin can deactivate an agent. Deactivated agents don't appear in mention autocomplete and don't execute on trigger.
- **agent-ux.AC1.6 Failure:** Non-admin users see "Not authorized" when accessing the agents settings page.
- **agent-ux.AC1.7 Failure:** Creating an agent with a duplicate display name within the same workspace returns a validation error.

### agent-ux.AC2: Agent mention autocomplete

- **agent-ux.AC2.1 Success:** Typing `@` in the rich text editor shows an "Agents" section in the mention dropdown alongside the existing "Users" section.
- **agent-ux.AC2.2 Success:** Agent suggestions filter as the user types, showing matching agent display names with a bot icon and type badge.
- **agent-ux.AC2.3 Success:** Selecting an agent inserts `@agent-name` into the editor content.
- **agent-ux.AC2.4 Success:** Posting a comment with `@builtin-agent-name` triggers the built-in execution task (not a webhook).
- **agent-ux.AC2.5 Success:** Posting a comment with `@external-agent-name` triggers a webhook (existing behaviour preserved).
- **agent-ux.AC2.6 Success:** Built-in agent's response appears as a comment on the issue with the bot user as actor.
- **agent-ux.AC2.7 Edge:** Mentioning a deactivated agent does not trigger execution or webhook.
- **agent-ux.AC2.8 Edge:** CE build shows no agent section in the mention dropdown (CE stub returns empty sections).

### agent-ux.AC3: Agent chat UI

- **agent-ux.AC3.1 Success:** A trigger button opens a right sidebar chat panel that persists across page navigation within the workspace.
- **agent-ux.AC3.2 Success:** Sending a message creates a conversation (or continues an existing one) and triggers the built-in agent.
- **agent-ux.AC3.3 Success:** Agent reasoning (thoughts), generated code (actions), tool call results (actions), and final responses stream into the panel in real-time via SSE.
- **agent-ux.AC3.4 Success:** Multi-turn conversation maintains context — the agent's second response accounts for the first exchange.
- **agent-ux.AC3.5 Success:** Elicitation cards render within the chat panel and submitting a response continues the agent's execution.
- **agent-ux.AC3.6 Success:** The agent can operate across the workspace — creating issues, querying cycles, assigning users — from within the chat panel.
- **agent-ux.AC3.7 Failure:** Agent operations respect the user's permissions. An operation the user can't perform manually fails with a clear error in the chat.
- **agent-ux.AC3.8 Edge:** If the SSE connection drops, the panel recovers by fetching missed activities and re-opening the EventSource.
- **agent-ux.AC3.9 Edge:** CE build has no chat panel trigger (CE stub returns null).

### agent-ux.AC4: Built-in agent runtime

- **agent-ux.AC4.1 Success:** LLM generates code that executes in a sandboxed subprocess. Tool calls within the code are intercepted via IPC and executed against the Django ORM.
- **agent-ux.AC4.2 Success:** Each execution step creates the correct `AgentRunActivity` type: thoughts as `thought`, code/tool calls as `action`, final output as `response`, failures as `error`.
- **agent-ux.AC4.3 Success:** Response activities auto-create `IssueComment` records when the run is issue-scoped (mention-triggered).
- **agent-ux.AC4.4 Success:** The tool registry generates correct markdown documentation and typed sandbox bindings from registered tool definitions.
- **agent-ux.AC4.5 Success:** Sandbox execution respects constraints: code size limit, tool call count limit, output size limit, wall-clock timeout, memory limit.
- **agent-ux.AC4.6 Failure:** A tool call for an operation the user lacks permission for returns a permission error to the sandbox (not a crash).
- **agent-ux.AC4.7 Failure:** Sandbox timeout kills the subprocess and marks the run as `failed` with an error activity.
- **agent-ux.AC4.8 Failure:** Invalid tool name in sandbox code returns a tool error (not a crash).
- **agent-ux.AC4.9 Edge:** Stale detection (existing Celery beat task) correctly marks inactive built-in agent runs as `stale`.

### agent-ux.AC5: SSE streaming

- **agent-ux.AC5.1 Success:** Creating an `AgentRunActivity` (from either agent type) pushes an SSE event to connected clients on the correct channel.
- **agent-ux.AC5.2 Success:** Run-level channels (`agent-run-{id}`) deliver only activities for that specific run.
- **agent-ux.AC5.3 Success:** Conversation-level channels (`agent-conversation-{id}`) deliver activities across all runs in that conversation.
- **agent-ux.AC5.4 Failure:** Unauthenticated SSE connections are rejected.
- **agent-ux.AC5.5 Failure:** SSE connections for runs in workspaces the user doesn't belong to are rejected.

### agent-ux.AC6: Cross-cutting behaviours

- **agent-ux.AC6.1:** All new API endpoints require authentication.
- **agent-ux.AC6.2:** External agent infrastructure (webhooks, mention detection, activity posting) continues to work unchanged.
- **agent-ux.AC6.3:** HW/CE overlay pattern is maintained — all new UI has CE stubs.
- **agent-ux.AC6.4:** The built-in agent is reachable via both the chat UI and @mentions — same runtime, different trigger paths.

## Glossary

- **AgentConversation**: A database model grouping multiple `AgentRun` records into a single multi-turn chat session, scoped to a workspace and user.
- **AgentConversationMessage**: A database model representing one turn in an `AgentConversation` — either a user message or the agent's response, with an optional link to the `AgentRun` that produced it.
- **AgentProfile**: The registered identity of an agent within a workspace. Stores display name, type (external or built-in), webhook URL (external only), and the associated bot user account.
- **AgentRun**: A single lifecycle-tracked execution of an agent — created when a trigger fires, transitions through `created → in_progress → completed/failed/stale`.
- **AgentRunActivity**: A record within an `AgentRun` capturing one step of execution. Types: `thought` (LLM reasoning), `action` (code block or tool call result), `response` (final output), `elicitation` (prompt requesting user input), `error`.
- **ASGI**: Asynchronous Server Gateway Interface. Python's async web server standard, required for SSE (long-lived HTTP connections) and WebSockets.
- **bubblewrap**: A Linux sandboxing tool using namespaces and seccomp filters. One of two candidate sandbox runtimes for isolating agent code execution.
- **Celery**: Python distributed task queue. The built-in agent execution runs as a Celery task, decoupling it from the HTTP request cycle.
- **Celery beat**: Celery's periodic task scheduler. Used for `detect_stale_agent_runs` and `cleanup_ephemeral_activities` scheduled jobs.
- **CE (Community Edition)**: The open-source, publicly distributed build of Plane. Features exclusive to HW are replaced with no-op stubs in CE.
- **Deno**: A JavaScript/TypeScript runtime with a permission model that can restrict filesystem, network, and subprocess access. One of two candidate sandbox runtimes.
- **django-eventstream**: A Django library providing SSE support via Redis pub/sub, integrating with ASGI. Used to stream `AgentRunActivity` records to the frontend in real-time.
- **DRF**: Django REST Framework. The library powering Plane's REST API serializers, views, and permission classes.
- **elicitation**: An activity type where the agent pauses execution and requests additional information from the user. Rendered as an interactive card in both the issue timeline and the chat panel.
- **EventSource**: The browser Web API for consuming SSE streams. Opens a persistent HTTP connection and receives server-pushed events.
- **HW (Hardware Edition / fork)**: The name for this fork's enterprise feature layer. Lives in `apps/web/hw/` (frontend) and `plane.hw` (backend). All features in this design are HW-only.
- **HW/CE overlay pattern**: The build-time mechanism by which `@/plane-web/` resolves to either `apps/web/hw/` or `apps/web/ce/`. Core code imports from the alias; the correct implementation is selected at build time.
- **IPC**: Inter-Process Communication. In this design, the JSON-lines protocol over stdin/stdout between the sandbox subprocess and the host Celery process.
- **IssueComment**: An existing Plane model for comments on issues. Built-in agent `response` activities auto-create `IssueComment` records when a run is issue-scoped (mention-triggered).
- **LiteLLM**: A Python library providing a unified interface to multiple LLM providers (Anthropic, OpenAI, Gemini, etc.), normalising API differences.
- **MobX**: A reactive state management library for JavaScript. Plane's frontend stores use MobX observable patterns; new stores in this design follow the same approach.
- **MCP (Model Context Protocol)**: A protocol for exposing tools and data to LLM agents in a standardised way. Out of scope for this design (blocked by an upstream OAuth dependency).
- **Phoebe**: An open-source AI trust and safety agent for the AT Protocol (Bluesky). Used as architectural inspiration for the code-generation sandbox approach.
- **prompt caching**: An Anthropic API feature that caches the stable prefix of a prompt (system instructions, tool documentation) server-side, reducing latency and cost on multi-turn interactions.
- **Redis pub/sub**: Redis's publish/subscribe messaging feature. `django-eventstream` uses it to fan out events from Celery workers to ASGI processes holding SSE connections.
- **sandbox**: An isolated execution environment for running LLM-generated code without direct access to the host filesystem, network, or database.
- **seccomp**: Linux kernel feature for filtering system calls. Used by bubblewrap to restrict what the sandboxed process can do at the OS level.
- **SSE (Server-Sent Events)**: A standard HTTP mechanism for servers to push events to a browser client over a single long-lived connection. Unidirectional (server to client only).
- **SWR**: A React data fetching library (stale-while-revalidate). Used alongside MobX stores for caching API responses in Plane's frontend.
- **ToolContext**: A Python object passed to every tool call carrying the triggering user, workspace, and current `AgentRun`. Permissions are enforced via this context.
- **ToolRegistry**: The Python decorator-based registry where tools declare their name, schema, and implementation. Generates both LLM-readable markdown and typed sandbox bindings from the same source.
- **`useAdditionalEditorMention`**: The HW overlay hook that injects additional sections (agents) into the rich text editor's @mention dropdown. The CE stub returns empty sections.
- **webhook**: An HTTP callback — the external agent integration model. When a mention triggers an external agent, Plane POSTs the event to the agent's registered URL.

## Architecture

Four components connected by shared data models and a real-time streaming layer.

### Built-in agent runtime

The runtime is a Celery task that orchestrates an LLM conversation loop with sandboxed code execution. When triggered (via chat message or @mention), it:

1. Loads system prompt with tool documentation and workspace context.
2. Sends the user's message to the LLM via LiteLLM (existing infrastructure).
3. Receives a code block from the LLM.
4. Spawns a sandboxed subprocess with restrictive permissions.
5. The sandbox executes the code, calling Plane API tools via an IPC bridge (JSON lines over stdin/stdout).
6. Each tool call is intercepted by the host process, validated against the tool registry, and executed against the Django ORM with the triggering user's permissions.
7. Results stream back to the frontend via SSE as `AgentRunActivity` records.
8. The loop continues until the LLM produces a final response or hits a safety limit.

The sandbox runtime (Deno or bubblewrap — deferred to implementation) provides the isolation boundary. The tool registry provides the permission boundary. Neither the sandbox nor the LLM has direct database access.

### Tool registry

A Python decorator-based registry where each tool declares its name, description, parameter schema, and return schema. At startup, the registry generates:

- **Markdown documentation** injected into the LLM system prompt.
- **Typed bindings** (TypeScript declarations or Python stubs) written to the sandbox's import path.

Tools execute within a `ToolContext` carrying the triggering user, workspace, and current `AgentRun`. Permission enforcement reuses existing DRF permission patterns — a user who can't create issues in a project can't do it via the agent either.

MVP tool set (~18 tools): issue CRUD + search, comment list/create, project list/get, cycle and module list/get/add_issues, user list/search, label list, state list.

### IPC protocol

Sandbox and host communicate over stdin/stdout using newline-delimited JSON:

```
Sandbox → Host:
  {"type": "tool_call", "id": "call_1", "name": "issues.create", "params": {...}}
  {"type": "output", "content": "..."}
  {"type": "error", "message": "..."}

Host → Sandbox:
  {"type": "tool_result", "id": "call_1", "result": {...}}
  {"type": "tool_error", "id": "call_1", "error": "..."}
```

Sandbox constraints (configurable, sane defaults): 50K character code limit, 25 tool calls per execution, 1MB output limit, 60-second wall-clock timeout, 256MB memory.

### SSE streaming layer

`django-eventstream` with Redis pub/sub bridges activity from Celery workers to the ASGI server. The Celery task creates an `AgentRunActivity` (DB write), then calls `send_event()` which publishes via Redis. The ASGI server pushes events to connected `EventSource` clients.

Channel naming:

- `agent-run-{run_id}` — single run (mention-triggered).
- `agent-conversation-{conversation_id}` — all runs within a chat session.

Fallback: if the SSE connection drops, the frontend fetches all activities for the run to catch up, then re-opens the EventSource.

### Chat UI

A right sidebar panel (~400px, resizable) that persists across navigation. Operates at workspace scope — the agent works across projects and issues from one conversation.

Each user message creates or continues an `AgentConversation` and triggers a new `AgentRun` within it. Previous messages form the LLM context window for multi-turn dialogue. Activities stream into the panel via SSE as the agent executes.

The panel reuses existing activity renderers (ThoughtRenderer, ActionRenderer, ErrorRenderer, ElicitationCard) and adds a code block renderer for action activities showing generated code.

### Agent management UI

A workspace settings page at `/settings/agents/` following the webhook management pattern: list view with cards, detail view with forms, create modal for external agents. Handles both external (webhook) and built-in (internal) agent types.

The built-in agent is auto-seeded per workspace and can't be deleted — only configured (model override, tool permissions, active toggle). External agents get the full CRUD flow with API token generation on creation.

### Mention autocomplete

The HW overlay hook (`useAdditionalEditorMention`) returns an "Agents" section in the @mention dropdown, fetching active agents and displaying them alongside users. On selection, the editor inserts `@agent-name`. The backend mention detection in `comment.py` routes to either webhook dispatch (external) or internal execution task (built-in) based on `agent_type`.

## Existing patterns

### Webhook settings UI → agent management UI

The webhook management UI (`apps/web/core/components/web-hooks/`) provides the exact template: `SettingsHeading` with CTA button, card list with item components, detail page with React Hook Form, two-phase create modal (form → secret display), `WebhookStore` with `Record<string, IWebhook>` shape, `WebhookService` extending `APIService`. The agent management UI follows this pattern for external agents.

### Bot user system → built-in agent identity

`User.is_bot` and `User.bot_type` with `BotTypeEnum` already exist (migration 0084). The workspace seed task (`apps/api/plane/bgtasks/workspace_seed_task.py`) demonstrates bot user creation. The built-in agent follows this pattern with `bot_type=AGENT`.

### Agent infrastructure → run lifecycle and activities

`AgentProfile`, `AgentRun`, `AgentRunActivity` models already exist in `apps/api/plane/hw/models/agent.py` with full CRUD views, serializers, and URL routing. Status transitions are validated at the model level. The design extends this infrastructure rather than replacing it.

### Mention overlay hook → autocomplete extension

`useAdditionalEditorMention` in `apps/web/hw/hooks/use-additional-editor-mention.tsx` is the HW overlay hook for injecting additional mention sections. The CE stub at `apps/web/ce/hooks/use-additional-editor-mention.tsx` returns empty sections. The `MentionsListDropdown` in the editor package already renders multiple sections with icons and subtitles.

### LiteLLM backend → LLM dispatch

The existing `get_gpt_response()` function in `apps/api/plane/app/views/external/base.py` dispatches to LLM providers via LiteLLM. The built-in agent runtime reuses this dispatch layer for model calls, inheriting provider configuration from instance admin settings.

### AgentRunPanel → chat UI building blocks

Activity renderers in `apps/web/hw/components/issues/agent/activity-renderers.tsx` (ThoughtRenderer, ActionRenderer, ErrorRenderer, ResponseRenderer) and the ElicitationCard handle rendering of all activity types. The chat UI reuses these components within a new conversational layout.

### HW/CE overlay pattern

All new UI lives in `apps/web/hw/`. CE stubs return `null` or empty implementations matching the same TypeScript interface. The agent chat panel, management settings page, and mention hook all follow this pattern.

### Phase 3: Sandbox execution engine

**Goal:** Subprocess management, IPC protocol, and safety constraints for sandboxed code execution.

**Components:**

- `apps/api/plane/hw/agent_tools/sandbox.py` — `SandboxExecutor` class. Spawns subprocess (Deno with `--allow-read` only, or bubblewrap — chosen during implementation based on deployment constraints). Writes code to stdin, reads JSON lines from stdout. Routes `tool_call` messages to the tool registry. Enforces constraints (code size, tool call count, output size, timeout, memory). Returns execution result (output text, tool call log, error if any).
- `apps/api/plane/hw/agent_tools/ipc.py` — JSON lines protocol: message types, serialisation, deserialisation, validation.
- Runtime files for sandbox (TypeScript or Python): tool call interface (`callTool()`), output interface, error handling. Bundled with the application.

**Dependencies:** Phase 2 (tool registry for routing tool calls).

**Done when:** Sandbox spawns, executes code, and returns results. Tool calls route through the registry correctly. Timeout kills the subprocess. Code size / tool call / output limits are enforced. Tests cover happy path execution, tool call routing, timeout behaviour, and constraint enforcement.

### Phase 4: Built-in agent execution task

**Goal:** Celery task that orchestrates the full LLM → sandbox → tools loop and creates activity records.

**Components:**

- `apps/api/plane/bgtasks/builtin_agent_task.py` — `builtin_agent_execute_task` Celery task. Accepts `run_id` and trigger context (comment text or conversation messages). Constructs LLM prompt (system prompt + tool docs + context). Calls LiteLLM. Passes generated code to `SandboxExecutor`. Creates `AgentRunActivity` records for each step (thought, action, response, error). Manages run status transitions (created → in_progress → completed/failed). Handles multi-turn within a single run (LLM may generate multiple code blocks).
- `apps/api/plane/hw/agent_tools/prompts.py` — system prompt templates. Includes tool documentation (from registry), workspace context, and instructions for code generation format.
- Updates to `apps/api/plane/hw/views/agent.py` — conversation endpoints: create conversation, send message (triggers task), list messages.
- Updates to `apps/api/plane/hw/urls/agent.py` — conversation routes.

**Dependencies:** Phase 3 (sandbox executor), Phase 2 (tool registry for prompt generation), Phase 1 (conversation models).

**Done when:** A message sent to the conversation endpoint triggers the Celery task. The task calls LiteLLM, executes generated code in the sandbox, creates activity records, and transitions the run to a terminal state. Response activities create IssueComments when issue-scoped. Tests cover the full execution loop, error handling (LLM failure, sandbox timeout, tool errors), and activity creation.

## Additional considerations

**Sandbox runtime choice deferred.** The design supports either Deno (V8 permissions, TypeScript-native) or bubblewrap/seccomp (Linux-native, Python-friendly). The IPC protocol is language-agnostic. Implementation should evaluate both against the deployment environment (Docker Compose with Linux containers favours bubblewrap; standalone deployment may prefer Deno for portability).

**Prompt caching.** The system prompt (tool docs, workspace context) is stable across turns within a conversation. If using Anthropic models, leverage prompt caching to reduce latency and cost on multi-turn interactions. The prompt construction in `prompts.py` should separate cacheable (system + tools) from dynamic (conversation history) content.

**Tool set expansion.** The MVP set covers core project management operations. Future tools (pages, views, analytics, notifications) follow the same registry pattern — add a new module in `agent_tools/tools/`, register via decorator.

**Implementation scoping.** This design has exactly 8 phases. If any phase proves too large during implementation planning, consider splitting the plan into two implementation rounds (phases 1-5 for runtime infrastructure, phases 6-8 for UI).
