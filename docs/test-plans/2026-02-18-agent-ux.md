#### 3.2 Real Deno code execution

**What to verify:** A simple TypeScript code snippet actually executes inside the Deno subprocess, calls a tool via IPC, and returns output. The automated tests mock `subprocess.Popen`; this verifies the real Deno binary works.

**Steps:**

1. Start the Django shell inside the API container:
   ```bash
   docker compose exec api python manage.py shell
   ```
2. Run:
   ```python
   from plane.hw.agent_tools.registry import ToolRegistry, ToolContext
   from plane.hw.agent_tools.sandbox import SandboxExecutor
   from plane.hw.agent_tools.constraints import SandboxConstraints
   from plane.db.models import User, Workspace
   from plane.hw.models import AgentRun, AgentProfile
   # Use any existing user/workspace/run from your dev data
   user = User.objects.first()
   workspace = Workspace.objects.first()
   agent = AgentProfile.objects.first()
   run = AgentRun.objects.first()
   context = ToolContext(user=user, workspace=workspace, run=run)
   registry = ToolRegistry()
   executor = SandboxExecutor(registry, context, SandboxConstraints(timeout_seconds=10))
   result = executor.execute('output("hello from deno");')
   print(result.output, result.error, result.timed_out)
   ```

**Expected behaviour:** `result.output` is `"hello from deno"`, `result.error` is `None`, `result.timed_out` is `False`.

**Why it can't be automated:** Requires a running container with Deno installed.

#### 3.3 Sandbox timeout kills subprocess

**What to verify:** An infinite loop actually times out after `timeout_seconds` and `result.timed_out` is `True`.

**Steps:** Run the shell snippet from 3.2 but use:

With `SandboxConstraints(timeout_seconds=3)`.

**Expected behaviour:** After ~3 seconds, `result.timed_out` is `True`, no exception raised.

**Why it can't be automated:** Requires real subprocess + Deno.

### Phase 5 — SSE real-time streaming

2. Open devtools → Network and find the `events/` SSE connection for the conversation.
3. Send a second message in the same conversation.

**Expected behaviour:** Both the first and second run's activities arrive on the same SSE connection.

**Why it can't be automated:** Same as 5.1.

#### 5.3 SSE connection refused for non-owners

**What to verify:** A user who is not the conversation owner cannot connect to the conversation SSE endpoint.

#### 5.4 SSE reconnect recovery

**What to verify:** AC3.8: when the SSE connection drops, the chat panel fetches missed activities and re-opens the `EventSource`.

**Steps:**

3. Send a message from the server side (via Django shell or API) that creates activities.
4. Observe the frontend.

**Expected behaviour:** Within a few seconds, the panel reconnects (you can see a new SSE request in Network), and the missed activities appear in the message list.

**Why it can't be automated:** Requires browser interaction to simulate network drops.
